# exec-plan

新しい exec-plan を起票するときに使うスキル。
plan は実装着手の判断基準と review checkpoint を兼ねる。
曖昧な plan は review の意味を失わせ、未来の読み手（自分含む）が「何が決まっていて何が宙ぶらりんか」を読み取れなくなる。
このスキルは **意図 + 権衡 + 検証可能性** を担保することを目的とする。

## やること

1. `docs/exec-plans/active/YYYY-MM-DD-<short-topic>-plan.md` を新規作成する。
   - 日付は plan 起票日（実装日ではない）。
   - slug は kebab-case、ASCII、5 単語以内。
   - 例: `2026-05-20-firestore-reading-repository-plan.md`
2. 同ディレクトリの `template.md` の内容をそのままコピーして埋める。
3. **全項目を残し、空欄にしない**。書かない理由がある項目は `N/A: <理由>` と書く（書き忘れと区別するため）。
4. 各セクションの書き方は下記「セクション別ガイド」に従う。
5. 書き終えたら「チェックリスト」を自分で確認してから review に出す。
6. `Review status: pending` の間は実装に着手しない。

## セクション別ガイド

### Goal

- 3 行以内。
- **技術的に何を変えるか** を書く。実装後のリポジトリの状態をイメージできること。
- ビジネス価値は書かない。それは product-spec の役割。
- OK 例: 「frontend HTTP client にデフォルトタイムアウトを追加し、abort 時に retryable な `ApiClientError` を返す」
- NG 例: 「ユーザー体験を向上させる」（← 何を変えるかが書かれていない）

### Non-Goals

- 最低 2 項目。
- 「今回やらないこと」を具体的に書く。境界の認識合わせが目的。
- OK 例: 「UI 画面の再設計はしない」「backend のタイムアウトポリシーは変えない」

### 影響範囲

- `files_to_modify` / `files_to_create` / `files_to_delete` に分けて列挙。
- 各ファイルに **1 行 reason** を付ける。
- 削除する場合は **代替先を必ず添える**。

### 実装ステップ

- **3〜7 個** に分割する。
- 1 ステップ = 1 つの責務。独立 review 単位として成立すること。
- 各ステップに以下を必ず書く:
  - **内容**: 何をするか
  - **完了条件**: 観測可能な事実として終わったと判断する基準
  - **検証方法**: どのコマンド / テスト / 目視で確認するか

### 接口定義

- 新規 / 変更される型・関数・API・data schema は **必ずコードブロックで書く**。
- 散文での field 説明は禁止（例「name は文字列で省略可能」← NG）。
- Go の struct、TypeScript の type、HTTP endpoint の signature、JSON schema など、機械的に検査可能な形式で書く。
- 変更がない場合のみ「変更なし」と書いてよい。

### 検討した代替案

- **最低 2 案**。
- 各案に **却下理由** を書く。曖昧形容詞は禁止（「複雑すぎる」「微妙」「将来的に」など）。
- 却下理由には **観測可能な事実 / 測定可能な値 / 既存ドキュメントへの参照** を含める。
- OK 例: 「Firestore の write 上限 500/s を見積もり段階で超える可能性がある」「対応 SDK が v2 系のみで、現在使用中の v1 系と API 互換性がない」
- NG 例: 「scale しない気がする」「将来的に困りそう」

### Open Questions

- 未決事項に `[OPEN]` ラベルを付ける。
- review で必ず回収する。**回収方法（誰がいつ決めるか）も書く**。

## チェックリスト

書き終えたら自分で確認してから review に出す。

- [ ] Goal が 3 行以内で、ビジネス価値ではなく技術変更を書いている
- [ ] Non-Goals が 2 項目以上ある
- [ ] 影響範囲の各ファイルに 1 行 reason が付いている
- [ ] 削除ファイルには代替先が書かれている
- [ ] 実装ステップが 3〜7 個で、各ステップに完了条件と検証方法がある
- [ ] 接口定義が code block で書かれていて、散文の field 説明が存在しない
- [ ] 代替案が 2 件以上あり、各却下理由が観測可能な事実を含む
- [ ] 「将来的に」「TBD」「あとで」「うまく」「いい感じに」「適切に」が本文に存在しない
- [ ] 意図（なぜ）と計画（何を）が分離されている
- [ ] `[OPEN]` の項目には誰がいつ決めるかが書かれている
- [ ] frontmatter が埋まっている（特に `affected_modules` と `last_verified`）

## アンチパターン

次の表現は使わない / 修正対象。

| パターン | 修正方針 |
| --- | --- |
| 「将来的に対応する」 | Non-Goals に移すか、別 plan を起票する |
| 「TBD」 | `[OPEN]` ラベル + 誰がいつ決めるかを明記 |
| 「いい感じに」「うまく」「適切に」「なるべく」 | 具体的な数値・条件・コマンドに置き換える |
| Goal に業務価値を書く | product-spec で書く |
| 「複数の選択肢があるが」+ 結論なし | 代替案として明示して却下理由を書く |
| Goal の中に Non-Goals や実装ステップを混ぜる | セクションを分離する |
| 散文で field 説明 | code block で type signature を書く |
| 代替案の却下理由が形容詞のみ | 観測可能な事実 / 数値 / 参照リンクで根拠を示す |

## 完了後の運用

- 実装中: plan の checklist と変更内容を更新する。
- 実装完了: `docs/exec-plans/completed/` へ移動し、`Completion` セクションを埋める（削除しない、ハードルール）。
- 設計判断を変えた場合: plan に追記するのではなく、**新しい plan を起票して旧 plan の frontmatter を `status: superseded` に変える**（`superseded_by` で新 plan へリンク）。
