# product-spec

新しい product-spec を起票するときに使うスキル。
product-spec は **「何を作るか（What）」と「なぜ作るか（Why）」** を残す文書で、Living docs（継続更新可）として扱う。
**実装方法（How）は書かない** — それは exec-plan の役割。spec と plan を混ぜると、spec が「実装が変わるたびに書き直す」破壊的更新の対象になり、意図の履歴が失われる。

## やること

1. `docs/product-specs/<feature-slug>.md` を新規作成する。
   - slug は kebab-case、ASCII、機能の本質を 2〜5 単語で表す。
   - 日付 prefix は **付けない**（spec は dated artifact ではない）。
   - 例: `guided-intake.md`, `trend-tarot-experience.md`
2. 同ディレクトリの `template.md` の内容をコピーして埋める。
3. **全項目を残し、空欄にしない**。書かない理由がある項目は `N/A: <理由>` と書く。
4. 各セクションの書き方は下記「セクション別ガイド」に従う。
5. 書き終えたら「チェックリスト」を自分で確認してから review に出す。

## セクション別ガイド

### Summary

- Feature name: ユーザーが認識する名前（社内コードネームではなく）
- 一行説明: 「誰が」「何のために」使う機能か。30 字以内目標
- Status: `draft` / `active` / `obsolete`

### User Story / 解決する問題

- 「誰の」「どんな状況で」「どんな課題を」「どう解決する」の 4 要素を書く
- ユーザーの**現状の苦痛 / 不便 / 機会損失**を具体的に書く
- 「便利になる」「使いやすくなる」のような曖昧表現は禁止

### 成功指標

- **測定可能な指標を最低 2 つ**。
- 各指標に **観測方法**（どの metric / log / event / アンケート結果を見るか）を必ず添える。
- 観測できない指標は書かない（書いても評価できないため）。
- OK 例: 「セッション開始から最初の reading 完了まで 60 秒以内（観測: `session_duration_ms` event の p50）」
- NG 例: 「ユーザー満足度が上がる」（測定方法なし）

### ユーザーシナリオ

- **具体的なシナリオを最低 2 つ**。
- 「典型的なユーザー」「一般的な使い方」のような抽象表現は禁止。**人物像と前提状況を書く**。
- 各シナリオは「ユーザー → システム → 結果」の流れで書く。
- happy path だけでなく、**想定される分岐や失敗** も最低 1 シナリオ含める。

### スコープ

- **Included**: 今回作るもの。具体的に列挙する。
- **Excluded（今回やらないこと）**: スコープ境界。**各項目に「なぜ今回やらないか」の理由を添える**。

### 失敗モード / Edge cases

- happy path 以外のパターンを列挙。
- 失敗（例: ネットワーク断、外部 API timeout、入力不足、権限不足）に対する **期待動作** を書く。
- 「いい感じに失敗する」のような曖昧表現は禁止。

### 他 spec / plan との関係

- **依存する spec**: この機能を前提に動く他 spec
- **この spec を実装する plan**: 既存 / 予定の exec-plan へのリンク
- **影響を受ける既存 spec**: 本 spec によって挙動が変わる既存機能

### Open Questions

- 未決事項に `[OPEN]` ラベルを付ける。
- **回収方法（誰がいつ決めるか）も書く**。

## チェックリスト

書き終えたら自分で確認してから review に出す。

- [ ] User Story の「誰の / 状況 / 課題 / 解決」4 要素が揃っている
- [ ] 成功指標が 2 つ以上あり、各指標に観測方法が書かれている
- [ ] ユーザーシナリオが 2 つ以上あり、各シナリオに具体的な人物像と状況がある
- [ ] シナリオの 1 つ以上が失敗 / 分岐パターンを含む
- [ ] Excluded の各項目に「なぜ今回やらないか」の理由が書かれている
- [ ] 失敗モード / Edge cases に最低 3 ケースが挙がっている
- [ ] 実装詳細（具体的なライブラリ名、ファイルパス、SQL、コード）が本文に含まれていない
- [ ] 「便利」「使いやすい」「いい感じに」「適切に」が本文に存在しない
- [ ] frontmatter が埋まっている（特に `owner` と `last_verified`）
- [ ] 関連する exec-plan / 他 spec へのリンクが書かれている

## アンチパターン

| パターン | 修正方針 |
| --- | --- |
| 「便利になる」「使いやすくなる」 | 測定可能な成功指標に置き換える |
| 実装詳細（ライブラリ名、テーブル名、関数名）を spec に書く | exec-plan に移す |
| 「典型的なユーザーが ...」 | 具体的な人物像（ロール、状況、前提知識）を書く |
| 成功指標に観測方法がない | どの metric / event / アンケートを見るか書く |
| Excluded に理由がない | 「なぜ今回やらないか」を 1 行添える |
| happy path しか書かない | 失敗・分岐シナリオを最低 1 つ追加 |
| 「将来の拡張のために」 | Open Questions に移すか、別 spec として後日起票 |
| Summary 1 行説明が長い（50 字超） | 機能の本質を 30 字以内に絞る |

## 完了後の運用

- product-spec は **Living docs**。実装やユーザー学習に伴って更新する。
- 更新時は `last_verified` を当日日付に更新する。
- 機能が廃止された場合は `status: obsolete` にし、`obsolete_reason` を frontmatter に追記。**削除しない**（過去の意図を辿れるよう残す）。
- 大きな方針転換が必要な場合は、新しい spec ファイルを作り、旧 spec を `status: obsolete` にしてリンクで繋ぐ。
